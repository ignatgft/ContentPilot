# CONTENTPILOT — ЭТАП 4: AI CREATIVE STUDIO
## Генерация рекламных фото, изображений и видео для бизнеса

### 1. Твоя задача

Ты — senior full-stack engineer, AI integration architect и специалист по созданию коммерческих AI-продуктов.

Работаешь с существующим репозиторием:

https://github.com/ignatgft/ContentPilot.git

Ветка: `main`.

ContentPilot — платформа для автоматизации маркетинга малого бизнеса.

Текущий технологический стек:
- Backend: Java 21, Spring Boot 3.3.4.
- Database: PostgreSQL.
- Web: React 19, TypeScript, Vite, Tailwind CSS.
- Mobile: Flutter, Riverpod, Android.
- Infrastructure: Docker Compose, Nginx, Cloudflare Tunnel.
- AI-тексты и сценарии: существующая интеграция Claude.
- Планировщик: существующий механизм на PostgreSQL и Spring Scheduler.
- Защита от ошибок: существующие память бренда и VerificationService.

Перед началом обязательно проверь актуальное состояние кода. Не считай описание архитектуры гарантией того, что все заявленные функции реализованы именно так: подтверди это в исходниках.

**Цель этапа:** расширить существующую платформу профессиональной AI-студией, где предприниматель сможет создавать рекламные фотографии, визуалы товаров, обложки, баннеры и короткие рекламные видео, соответствующие стилю его бренда.

Не создавай отдельное приложение. Новый функционал должен интегрироваться в существующие веб-версию, мобильное приложение, профиль бренда, генератор кампаний, контент-календарь и публикации.

Не ограничивайся планом и макетами. Реализуй работающие функции, интеграции, обработку ошибок, тесты и документацию.

### 2. Новая концепция продукта

Добавь в ContentPilot новый раздел:

**AI Creative Studio — рекламный контент для бизнеса за несколько действий.**

Пользователь сможет выбрать один из режимов:

1. Генерация рекламного фото.
2. Создание баннера или обложки.
3. Создание серии изображений для кампании.
4. Редактирование существующего изображения.
5. Создание короткого рекламного видео.
6. Превращение фотографии товара в короткий видеоролик.
7. Создание комплекта материалов для продвижения товара или услуги.

Главный сценарий:

Пользователь выбирает бренд, загружает фото товара или вводит задачу. Система использует информацию о бизнесе, предлагает идею, создаёт текстовый промпт, генерирует изображение или видео и предоставляет результат для редактирования, скачивания либо добавления в публикацию.

Пример:

Владелец кофейни загружает фотографию сезонного латте.

Он выбирает цель: продвинуть напиток на выходных.

ContentPilot подготавливает рекламную концепцию, создаёт визуалы для социальных сетей, генерирует короткий видеоролик и предлагает рекламный текст с призывом к действию.

Пользователь проверяет материалы и может добавить их в существующую контент-кампанию.

### 4. Интеграция моделей генерации изображений

Реализуй отдельный серверный интерфейс генерации изображений.

Предпочтительная структура:

- `ImageGenerationProvider`
- `ImageGenerationRequest`
- `ImageGenerationResult`
- `ImageGenerationService`
- `ImageGenerationProviderRegistry`

Названия можно адаптировать к существующим правилам проекта.

Провайдер должен поддерживать доступные возможности используемой модели:

- Генерацию изображения из текстового описания.
- Генерацию на основе фотографий-референсов.
- Редактирование существующего изображения.
- Генерацию нескольких вариантов, если это поддерживается.
- Настройку разрешения, качества и соотношения сторон.
- Получение результата, ошибок и метаданных.

Выбирай провайдера и модель с учётом реальной доступности API, стоимости, региона и текущих официальных ограничений.

В качестве кандидата исследуй актуальный OpenAI Images API с поддерживаемой моделью GPT Image. Не полагайся на устаревшие названия моделей. Перед реализацией сверь используемые модели и параметры с актуальной официальной документацией.

Ключи API должны храниться только на сервере через переменные окружения или существующий безопасный механизм конфигурации.

Не вызывай платные генеративные API непосредственно из React или Flutter.

Claude остаётся ответственным за анализ бизнес-цели, написание текстов, подготовку концепций и построение промптов. Саму генерацию изображения выполняет специализированный image provider.

### 5. Создание рекламных фотографий

Это первая функциональность, которую необходимо реализовать полностью.

Пользователь должен иметь возможность выбрать бренд и тип материала:

- Фото продукта для интернет-магазина.
- Рекламное фото для социальных сетей.
- Lifestyle-сцена с товаром.
- Изображение блюда или напитка.
- Рекламный баннер.
- Обложка публикации.
- Визуал новой коллекции.
- Афиша мероприятия.
- Карточка товара.
- Изображение для акции или специального предложения.

Предусмотри настройку:

- Цели изображения.
- Целевой аудитории.
- Стиля фотографии.
- Фоновой сцены.
- Освещения и композиции.
- Цветовой палитры бренда.
- Формата и соотношения сторон.
- Качества итогового материала.
- Необходимых вариантов изображения.

Добавь возможность загружать собственную фотографию товара в качестве референса.

Примеры задач:
- «Создай рекламное фото этого латте в уютной современной кофейне».
- «Размести этот товар в минималистичной студийной композиции».
- «Создай сезонный рекламный визуал в цветах нашего бренда».
- «Подготовь изображение товара для публикации в социальных сетях».

Результат должен соответствовать контексту бизнеса, а не быть случайным изображением по общему описанию.

Если модель не может гарантировать точное сохранение товара, предупреди об этом пользователя и предоставь возможность проверить результат.

Не представляй сгенерированную концепцию как гарантированно точное фото реального товара.

### 6. Сохранение фирменного стиля

Интегрируй генерацию изображений с существующей памятью бренда.

Для построения промпта используй только доступные и релевантные данные:

- Цвета бренда.
- Визуальный стиль.
- Целевую аудиторию.
- Тип бизнеса.
- Категорию продукта.
- Загруженные референсы.
- Тон маркетинговых коммуникаций.
- Предпочтения пользователя.

Добавь систему формирования структурированного промпта.

Не передавай модели все сведения о бизнесе без разбора. Выбирай данные, необходимые для конкретного задания.

Например, для кофейни важны оформление напитка, посуда, атмосфера заведения и визуальный стиль. Для магазина одежды — особенности товара, ткань, силуэт и требуемая композиция.

Раздели в системе:

1. Факты о товаре.
2. Описание визуального стиля.
3. Инструкции по композиции.
4. Текст рекламного предложения.
5. Технические параметры результата.

Изменение визуального стиля не должно менять подтверждённые характеристики товара.

### 7. Точный текст, цены и логотипы

Не полагайся на модель изображений для безошибочного написания названий брендов, цен, скидок и рекламных надписей.

Важные текстовые элементы необходимо добавлять отдельным детерминированным слоем после генерации изображения.

Если это соответствует существующему стеку, реализуй серверный рендеринг текстовых слоёв или SVG-шаблонов.

Поддерживай:

- Логотип.
- Название продукта.
- Подтверждённую цену.
- Подтверждённые условия акции.
- Призыв к действию.
- Контактные данные, если они необходимы.
- Цвета и шрифты бренда.

Используй только проверенные данные из памяти бренда или соответствующего объекта товара.

Если факты не подтверждены, не добавляй их автоматически.

Пользователь должен иметь возможность изменить положение, размер и оформление текста, если это поддерживается существующей системой редактирования.

Не позволяй автоматически исправлять цену по догадке модели.

Перед публикацией используй существующий `VerificationService` или эквивалентную серверную логику.

### 8. Редактирование изображений

Добавь полноценный процесс доработки сгенерированного результата.

Доступные операции зависят от выбранного провайдера, но должны включать поддерживаемые API действия:

- Изменить фон.
- Изменить визуальный стиль.
- Сделать освещение мягче или ярче.
- Изменить композицию.
- Создать новый вариант.
- Использовать изображение как референс.
- Подготовить версию для другой площадки.
- Добавить отдельный текстовый слой.
- Перегенерировать результат по дополнительной инструкции.

Редактирование должно сохранять связь с исходным изображением.

Храни историю версий, чтобы пользователь мог вернуться к предыдущему варианту.

Не перезаписывай оригинал без явного действия пользователя.

Если операция недоступна для выбранной модели, покажи понятное сообщение и предложи доступный альтернативный сценарий.

### 9. Создание коротких рекламных видео

После полноценной реализации генерации изображений переходи к видеогенерации.

Реализуй отдельный интерфейс:

- `VideoGenerationProvider`
- `VideoGenerationRequest`
- `VideoGenerationResult`
- `VideoGenerationService`

Исследуй актуальные официальные API генерации видео.

В частности, проверь Gemini Omni Flash через Gemini API и другие подходящие провайдеры, если это требуется доступностью, стоимостью и качеством.

Не используй отключённую Sora API и старые модели Veo 3.1 Preview.

Перед реализацией проверь действующие идентификаторы моделей, методы API, разрешённые регионы, лимиты, форматы результатов и условия использования.

Сделай провайдер независимым от интерфейса приложения, чтобы позднее можно было добавить другого поставщика без переписывания бизнес-логики.

Видео генерируется асинхронно: запрос создаёт задачу, приложение получает её идентификатор и отслеживает статус до завершения.

Не удерживай HTTP-запрос открытым всё время генерации.

Пользователь должен иметь возможность:

- Создать видео по текстовому описанию.
- Анимировать исходную фотографию.
- Использовать изображение как визуальный референс.
- Выбрать доступную длительность ролика.
- Выбрать формат.
- Задать движение камеры.
- Уточнить атмосферу и стиль.
- Просмотреть результат.
- Скачать MP4.
- Повторить генерацию с другой инструкцией.
- Прикрепить ролик к публикации.

Начни с коротких роликов, которые подходят для продвижения товаров и услуг.

Не обещай неподдерживаемую длительность или разрешение — используй фактические параметры выбранной модели.

### 10. Автоматическая сборка видеоконтента

Создай workflow, который превращает бизнес-задачу в готовый видеоматериал.

Пример:

Пользователь задаёт цель: продвинуть сезонный напиток.

Система:

1. Анализирует бренд и задачу.
2. Генерирует идею ролика.
3. Создаёт короткий сценарий.
4. Разбивает сюжет на сцены, если это поддерживается выбранным workflow.
5. Подготавливает референсные изображения.
6. Генерирует видеоматериал.
7. Добавляет подтверждённые текстовые элементы.
8. При наличии подходящих компонентов генерирует озвучку.
9. Создаёт субтитры.
10. Формирует готовый файл для выбранной социальной сети.

Не пытайся реализовать все сложные возможности одновременно.

Первый работающий сценарий может быть таким:

Фотография товара → генерация короткого видео → добавление рекламного текста и логотипа → предварительный просмотр → скачивание.

После этого расширяй систему многокадровыми роликами, озвучкой и сложным монтажом.

Если в проекте уже есть сервис обработки медиа, используй его. Если нет, изучи возможность серверной сборки через FFmpeg. Проверь доступность бинарных файлов, конфигурацию Docker и требования к лицензированию перед интеграцией.

Оригинальные сгенерированные файлы необходимо сохранять отдельно от смонтированных результатов.

### 11. Асинхронные задачи и хранение результатов

Генерация видео и сложных изображений может занимать продолжительное время, поэтому создай надёжную серверную модель задач.

Если готового механизма нет, спроектируй таблицу задач генерации с полями, соответствующими архитектуре проекта:

- ID задачи.
- Пользователь.
- Бренд.
- Тип генерации.
- Провайдер и модель.
- Параметры запроса.
- Статус.
- Время создания и завершения.
- Ссылка на результат.
- Код и описание ошибки.
- Метаданные использования и стоимости, если доступны.

Используй реальные миграции БД и существующие правила именования проекта.

Предусмотри состояния:

- PENDING.
- PROCESSING.
- COMPLETED.
- FAILED.
- CANCELLED.

При необходимости добавь промежуточные состояния, соответствующие реальному провайдеру.

Учитывай, что названия состояний во внешнем API могут отличаться. Сопоставляй их с внутренней моделью.

Для фоновой обработки используй существующие механизмы PostgreSQL и Spring Scheduler либо другой уже реализованный компонент проекта. Не подключай Redis или Kafka без обоснованной необходимости и проверки архитектурных требований.

Обеспечь:

- Контролируемые повторы после временных ошибок.
- Ограничение времени ожидания.
- Защиту от повторного запуска одинаковой задачи.
- Корректную обработку превышения квот.
- Ограничение числа одновременных генераций.
- Безопасное хранение результатов.
- Очистку временных файлов.
- Логирование с идентификатором задачи без секретов.

Если внешний провайдер хранит результат ограниченное время, скачивай его в постоянное хранилище сразу после завершения генерации.

Используй существующее файловое или объектное хранилище, если оно имеется.

Если нет, добавь абстракцию хранения, позволяющую использовать локальное Docker-хранилище для разработки и внешнее объектное хранилище в production.

Не сохраняй большие файлы изображений и видео в строковых полях PostgreSQL без необходимости.

Пользователь должен иметь возможность просматривать историю собственных генераций и повторно открывать сохранённые результаты.

### 12. Backend API

Исследуй существующие маршруты перед добавлением новых.

При отсутствии подходящих контрактов реализуй согласованный API для следующих операций:

- Создать задачу генерации изображения.
- Создать задачу генерации видео.
- Получить статус задачи.
- Получить результат генерации.
- Отменить задачу, если операция поддерживается.
- Получить историю генераций пользователя.
- Получить сведения о сохранённом медиа.
- Удалить медиа по предусмотренным правилам.
- Создать изменённую версию существующего результата.
- Прикрепить изображение или видео к публикации.

Это перечень возможностей, а не требование дублировать уже имеющиеся эндпоинты.

Все операции должны проверять авторизацию, права доступа к бренду и принадлежность медиа конкретному пользователю или разрешённой команде.

Нельзя получать доступ к чужим изображениям или задачам, изменяя идентификаторы запросов.

Большие файлы загружай через предусмотренный механизм передачи медиа, учитывая лимиты размера и допустимые MIME-типы.

Не доверяй MIME-типу, указанному клиентом, без необходимой проверки содержимого.

Новые API должны быть документированы и использовать единый формат ошибок проекта.

### 16. Безопасность, стоимость и ограничения

Генерация изображений и видео может быть дорогой. Контролируй расходы на уровне пользователей и брендов.

Добавь конфигурируемые ограничения:

- Размер исходного файла.
- Количество одновременных задач.
- Число генераций за доступный период.
- Допустимые модели и качество.
- Ограничения на повторные запросы.
- Максимальное число вариантов за одну операцию.

Если возможно, используй реальные цены и метаданные использования провайдера. Если фактическая стоимость недоступна, не показывай выдуманные суммы.

Не позволяй клиенту обходить установленные лимиты путём многократного вызова API.

Не принимай API-ключи от провайдера со стороны мобильного клиента.

Для загруженных изображений учитывай права на использование материалов, конфиденциальность и допустимость обработки.

Не создавай автоматически изображения, которые приписывают бренду неподтверждённые свойства товара, результаты лечения, скидки или другие коммерчески значимые обещания.

Перед публикацией сохраняй проверку контента и предусмотренный режим пользовательского подтверждения.

### 19. Порядок реализации

Работай этапами, сохраняя работающий продукт.

**Фаза A — аудит и архитектура**

Изучи репозиторий, API, хранение медиа и существующие компоненты. Согласуй новые модели данных с текущими объектами бренда, кампании и публикации.

**Фаза B — генерация изображений**

Создай серверный провайдер, API, асинхронное выполнение при необходимости, сохранение результатов, экран генерации и галерею.

Добейся полноценного цикла: запрос → реальное изображение → сохранение → просмотр → скачивание.

**Фаза C — редактирование и стиль бренда**

Добавь фотографии-референсы, варианты, редактирование изображений и корректные текстовые слои.

**Фаза D — видеогенерация**

Подключи проверенный видеопровайдер, асинхронные задачи и скачивание результатов.

**Фаза E — создание рекламного ролика**

Реализуй минимальный сценарий сборки короткого видео с текстовыми элементами, затем постепенно добавляй озвучку и субтитры.

**Фаза F — интеграция с публикациями**

Добавь поддержку медиа в генератор кампаний, редактор, календарь и мобильное приложение.

**Фаза G — тестирование**

Исправь ошибки, проверь сборку и обнови документацию.

После каждой фазы сохраняй работоспособность существующих экранов и тестируй фактически реализованную функциональность.

### 20. Критерии завершения этапа

Этап считается завершённым не тогда, когда в интерфейсе появились новые кнопки, а когда пользователь способен пройти рабочий сценарий.

**Сценарий 1 — рекламное фото**

1. Пользователь входит в ContentPilot.
2. Выбирает бренд.
3. Загружает фотографию реального продукта.
4. Вводит рекламную задачу.
5. Система использует память бренда.
6. Сервер отправляет запрос реальному провайдеру генерации изображения.
7. Полученный результат сохраняется.
8. Пользователь просматривает и скачивает изображение.
9. При желании добавляет результат в пост.

**Сценарий 2 — рекламное видео**

1. Пользователь открывает Creative Studio.
2. Выбирает генерацию видео из фотографии.
3. Настраивает доступные параметры.
4. Создаётся серверная задача.
5. Пользователь видит статус выполнения.
6. Сервер получает видеорезультат и сохраняет его.
7. Пользователь просматривает ролик и скачивает MP4.
8. При желании прикрепляет его к публикации.

**Сценарий 3 — единая экосистема**

Сгенерированное медиа доступно в web и Flutter, сохраняется в библиотеке и подключается к текущему процессу подготовки и публикации контента.
