# ContentPilot: ТЗ этапа 2

Соцсети для публикации, мобильное приложение на Flutter для Android и доступ к бэкенду и фронтенду с телефона. Документ дополняет первое ТЗ для агента: стек, дизайн-кит, модель данных и правила безопасности остаются теми же.

## 1. Цели этапа

1. Публиковать из ContentPilot в VK, YouTube, Instagram и TikTok по тому же расписанию, что и в Telegram.
2. Сделать мобильное приложение на Flutter только под Android с теми же функциями, что у веб-версии, и полным набором ассетов (раздел 8).
3. Сделать так, чтобы бэкенд и фронтенд, запущенные на компьютере, были доступны с телефона всегда, пока компьютер включён.

Правило честности: если у площадки нет доступа к официальному API или приложение не прошло модерацию, пост получает режим «готово к публикации» (текст и медиа скачиваются), а не публикуется неофициальным обходом.

## 2. Общая архитектура публикаторов

- Интерфейс `Publisher` в пакете `publisher`: `connect()`, `publish(post)`, `fetchMetrics(post)`, `refreshToken()`, `capabilities()`.
- Реализации: `TelegramPublisher` (готово), `VkPublisher`, `YoutubePublisher`, `InstagramPublisher`, `TiktokPublisher`.
- `capabilities()` возвращает: поддерживаемые типы (текст, фото, видео), лимиты текста, нужно ли публичное медиа, нужна ли модерация приложения. Фронтенд и проверка контента берут правила из него, а не из жёстко прописанных значений.
- Подключение канала: OAuth-экран площадки, токены хранятся шифрованными в `channels`, статус канала `CONNECTED`, `EXPIRED`, `ERROR`. Просроченный токен: пост получает `FAILED` с понятной причиной, пользователь видит кнопку «Переподключить».
- Планировщик выбирает посты как раньше и вызывает нужный `Publisher` по полю `platform`. Атомарная смена статуса на `PUBLISHING`, до 3 попыток, запись в `publish_log`.
- Режим «готово к публикации»: статус `READY_MANUAL`, кнопка скачивания текста и медиа, ручная отметка «Опубликовано».
- Перед реализацией каждой площадки агент читает актуальную документацию API и фиксирует в `/docs/platforms/<название>.md`, какие версии и права использованы. Не полагаться на память о лимитах и правилах.

## 3. Медиа

- Хранилище файлов с публичными ссылками (S3-совместимое, например Cloudflare R2 или MinIO), локальная папка допустима только для разработки.
- Некоторые площадки забирают медиа по публичному URL, поэтому ссылка должна открываться из интернета. Для этого нужен проброс, описанный в разделе 6.
- Проверка типа и размера файла, лимиты на пользователя, удаление неиспользуемых файлов.
- Видео в MVP этапа 2 не генерируется: пользователь загружает готовый ролик, ContentPilot генерирует сценарий, подпись и хэштеги.

## 4. Площадки

### 4.1 VK

- Публикация на стену сообщества через официальный API (метод публикации записи, загрузка фото через сервер загрузки).
- Подключение: токен сообщества или VK ID OAuth с нужными правами, ID сообщества.
- Поддержка: текст, до нескольких фото, ссылка. Видео как отдельный шаг, если успеем.
- Метрики: просмотры, лайки, комментарии, репосты записи.
- Критерий: пост из календаря появляется на стене сообщества в заданное время.

### 4.2 YouTube (Shorts)

- Публикация видео через YouTube Data API v3 с OAuth.
- Заголовок, описание, хэштеги, приватность. Для Shorts вертикальный ролик подходящей длины по актуальным правилам YouTube.
- У API есть дневная квота, агент считает стоимость операций и показывает пользователю оставшийся лимит публикаций.
- Метрики: просмотры, лайки, комментарии.
- Критерий: загруженный ролик публикуется на канале с нужным заголовком и описанием.

### 4.3 Instagram

- Только официальный Instagram API (Graph API) для бизнес- или авторского аккаунта, связанного со страницей Facebook.
- Публикация в два шага: создать контейнер медиа, затем опубликовать. Медиа должно быть доступно по публичной ссылке.
- Поддержка: фото, Reels, подпись. Истории и карусели позже.
- Подключение через Facebook Login с нужными правами. Для работы с чужими аккаунтами приложение должно пройти проверку Meta; до этого работает только с аккаунтами тестировщиков. Агент пишет это в README, и на демо используется тестовый аккаунт.
- Метрики: охват, лайки, комментарии, сохранения (если доступны).
- Критерий: Reels или фото публикуются на тестовом аккаунте.

### 4.4 TikTok

- Официальный Content Posting API.
- Приложение должно пройти аудит TikTok. До аудита публикации по правилам платформы могут быть ограничены (например, только приватные), агент проверяет текущие правила в документации и показывает пользователю это ограничение в интерфейсе.
- Подключение через TikTok Login Kit, загрузка видео, заголовок, настройки приватности.
- Если доступ ограничен, используется режим «готово к публикации».
- Критерий: ролик публикуется на тестовом аккаунте или корректно уходит в `READY_MANUAL` с понятным сообщением.

### 4.5 Что менять во фронтенде и проверке

- Экран «Каналы»: карточка для каждой площадки со статусом, кнопкой подключения и пометкой «Живая публикация» или «Готово к публикации».
- Проверка контента: длина и формат берутся из `capabilities()`. Для каждой площадки свой предпросмотр поста.
- Журнал публикаций: платформа, статус, причина ошибки, ссылка на опубликованный пост.
- Аналитика: метрики по площадкам, пустые данные подписываются «данных пока нет».
- Значки площадок в дизайн-ките временные, заменить официальными по правилам каждой площадки.

## 5. Мобильное приложение на Flutter

### 5.1 Стек

- Flutter (stable), Dart, только Android. iOS на этом этапе не делаем.
- Состояние: Riverpod. Навигация: go\_router. Сеть: dio с перехватчиком обновления токена.
- Безопасное хранение токенов: flutter\_secure\_storage.
- Вход через Google: пакет google\_sign\_in, ID-токен проверяется на бэкенде.
- Тема: светлая и тёмная из токенов дизайн-кита (`tokens.json`), шрифт Manrope, интерактивные элементы не меньше 44 px. Статусы всегда с текстом.
- Иконки из `design-kit/icons` (SVG через flutter\_svg).
- Репозиторий: `/mobile`, адрес бэкенда в конфиге по окружениям (`dev`, `demo`, `prod`), не в коде.

### 5.2 Изменения в бэкенде для мобильного клиента

- Refresh-токен в cookie для мобильного неудобен. Добавить режим для мобильных клиентов: заголовок `X-Client: mobile`, тогда refresh-токен возвращается в теле ответа и принимается в теле запроса. Веб-режим с cookie не менять.
- Ротация refresh-токена и отзыв при выходе, привязка токена к устройству.
- CORS для мобильного не нужен, для веб-версии оставить список разрешённых адресов из настроек окружения.
- Версионирование API (`/api/v1`) уже есть, мобильное приложение работает только с ним.

### 5.3 Экраны (паритет с вебом)

1. Вход и регистрация (почта, пароль, Google).
2. Онбординг бренда.
3. Выбор цели кампании.
4. Кампания: карточки публикаций, предупреждения проверки, исправление, утверждение, публикация.
5. Календарь (список по дням, смена времени, на мобильном без сложного перетаскивания).
6. Каналы.
7. Аналитика.
8. Настройки: режим автономности, тема, язык, «Остановить всё».
9. Уведомления: пост опубликован, пост требует проверки, ошибка публикации. На первом шаге локальные уведомления и обновление при открытии, push через Firebase Cloud Messaging как следующий шаг.

Главное действие на мобильном: быстро утвердить кампанию и нажать «Остановить всё». Эти два сценария должны быть доступны в пару касаний.

### 5.4 Критерии приёмки мобильного

- Приложение собирается на Android, запускается на реальном телефоне и ходит в бэкенд по адресу из раздела 6.
- Вход почтой и Google работает, сессия переживает перезапуск приложения.
- Сценарий демо проходится с телефона: цель, неверная цена, исправление, утверждение, пост в Telegram.
- Обе темы работают на всех экранах.

## 6. Доступ к локальным бэкенду и фронтенду с телефона

Цель: проект запущен на компьютере, телефон открывает веб-версию и мобильное приложение работает с тем же бэкендом, откуда угодно, пока компьютер включён и онлайн.

### 6.1 Рекомендуемый вариант: Tailscale

Личная защищённая сеть между устройствами, без открытия портов в интернет.

1. Установить Tailscale на компьютер и на телефон, войти в один аккаунт.
2. Использовать имя устройства из Tailscale (MagicDNS) или его адрес из диапазона `100.x.x.x`.
3. Бэкенд (порт 8080) и фронтенд (порт 5173 или 3000) слушают на `0.0.0.0`, а не только на `localhost`. В Docker Compose порты публикуются на хост.
4. Вход в браузере телефона по адресу `http://<имя-устройства>:5173`, мобильное приложение берёт `http://<имя-устройства>:8080` из конфига окружения `demo`.
5. CORS бэкенда разрешает адрес фронтенда из настроек окружения.
6. Плюс: адрес стабильный, трафик закрыт от посторонних. Минус: Tailscale должен быть запущен на обоих устройствах.

### 6.2 Публичная ссылка, если она нужна (OAuth, Meta, TikTok, вебхуки, медиа по ссылке)

Google, Meta и TikTok требуют HTTPS-адрес и зарегистрированный адрес перенаправления, а Instagram и TikTok забирают медиа по публичной ссылке. Для этого подходит туннель:

- Cloudflare Tunnel с собственным доменом (стабильный адрес, бесплатно) или ngrok со статическим доменом. Одноразовые адреса, которые меняются при каждом запуске, для OAuth не годятся: при смене адреса его придётся каждый раз заново вносить в настройки площадок.
- Туннель запускается как служба, которая стартует вместе с системой и перезапускается при сбое (systemd, служба Windows или контейнер `restart: unless-stopped` в Docker Compose).
- Публиковать наружу только нужные пути: бэкенд, фронтенд и публичное медиа. Не публиковать базу данных, админку PostgreSQL и порты отладки.

### 6.3 Запасной вариант: одна Wi-Fi сеть

Телефон и компьютер в одной сети, адрес по локальному IP компьютера (`http://192.168.x.x:5173`). Открыть порты в файрволе только для локальной сети. Работает только дома, поэтому не подходит как «всегда доступно».

### 6.4 Чтобы было доступно всегда

- Службы поднимаются автоматически при старте компьютера (`restart: unless-stopped`).
- Компьютер не уходит в сон при подключении к питанию.
- Если компьютер выключен, сервис недоступен. Для демо надёжнее выложить бэкенд на хостинг (Render, Railway или VPS) с PostgreSQL и тем же Docker Compose. Агент подготавливает инструкцию развёртывания как резервный план.
- Эмулятор Android обращается к хосту по адресу `10.0.2.2`, а реальный телефон по адресу из 6.1 или 6.2.

### 6.5 Безопасность при публикации наружу

- Перед открытием наружу проверить, что нет паролей по умолчанию, отладочных страниц и открытых служебных адресов.
- Секреты только в переменных окружения, `.env` не в репозитории.
- Ограничение частоты запросов на вход, регистрацию и генерацию включено.
- Проверка владельца данных (`user_id`) в каждом запросе, токены каналов шифруются.
- Админские и служебные эндпоинты закрыты от внешнего доступа.

## 7. Порядок работ и критерии

| Этап | Что сделать | Критерий |
| --- | --- | --- |
| 1 | Интерфейс `Publisher`, `capabilities()`, статусы `READY_MANUAL`, экран «Каналы» по площадкам | Telegram работает через новый интерфейс, остальные площадки видны со статусом |
| 2 | Хранилище медиа с публичными ссылками | Загруженный файл открывается по ссылке извне |
| 3 | Доступ с телефона: Tailscale, адреса, службы с автозапуском | Веб-версия открывается на телефоне вне домашней сети |
| 4 | VK | Пост появляется на стене сообщества |
| 5 | Режим мобильных токенов в бэкенде | Мобильный клиент входит и обновляет сессию |
| 6 | Flutter: каркас, темы, вход, бренд, цель, кампания | Демо-сценарий проходится на телефоне |
| 7 | Flutter: календарь, каналы, аналитика, настройки, уведомления | Все экраны есть в обеих темах |
| 8 | YouTube, затем Instagram и TikTok (или `READY_MANUAL` при ограничениях) | Каждая площадка либо публикует, либо честно показывает режим «готово к публикации» |
| 9 | Резервное развёртывание на хостинг | Сервис открывается при выключенном компьютере |

После каждого этапа агент запускает проект с нуля и отчитывается: что работает, что проверено вручную, что не удалось и почему.

## 8. Android: платформа, ассеты и сборка

Платформа только Android, Flutter-проект в `/mobile`. Имя пакета: \[com.example.contentpilot, уточнить\]. Все ассеты лежат в `contentpilot-android-kit.zip`, агент раскладывает их по инструкции из `README.md` внутри архива.

### 8.1 Состав ассетов

- Иконка приложения: адаптивная (фон, основной слой и монохромный слой для тем Android 13+), круглая и обычная для старых версий, все размеры от mdpi до xxxhdpi.
- Иконка уведомлений `ic_stat_contentpilot`: белая на прозрачном фоне, как требует Android.
- Заставка при запуске: светлая и тёмная, для Android 12+ и для старых версий.
- 48 иконок интерфейса: SVG для Flutter и векторные XML для нативных мест.
- Логотипы (знак и логотип в обеих темах), 5 аватарок, значки площадок (временные, буквенные), баннеры 1200×630.
- Для Google Play: иконка 512×512 и графика функции 1024×500.
- Код: `app_theme.dart` (светлая и тёмная темы из токенов), `app_icons.dart` (константы `AppIcons` и виджет `AppIcon`), конфиги `flutter_launcher_icons.yaml` и `flutter_native_splash.yaml`.

### 8.2 Правила использования

- В интерфейсе иконки только через `AppIcon`, цвета только из `CpColors`. Свои иконки и цвета не добавлять.
- Векторные XML-иконки нужны только для нативных мест (уведомления, виджеты). Внутри Flutter использовать SVG.
- Шрифт Manrope (400, 500, 700, 800) агент скачивает с Google Fonts и кладёт в `assets/fonts/`, в архив он не входит.
- Интерактивные элементы не меньше 48 dp, статусы всегда с текстом.

### 8.3 Сеть и вход

- Android по умолчанию блокирует обычный http. Для разработки использовать `network_security_config.xml` из кита, он лежит в папке `debug` и в release-сборку не попадает.
- Для release и демо нужен HTTPS: либо HTTPS-адрес через Tailscale (включается в админке Tailscale, агент сверяется с актуальной документацией), либо туннель с доменом из раздела 6.2.
- Вход через Google: в Google Cloud создать Android OAuth client с именем пакета и SHA-1 ключа подписи, отдельно для debug и release. Бэкенд проверяет ID-токен по серверному client ID.

### 8.4 Уведомления и сборка

- Канал уведомлений `publish_status` («Статусы публикаций») создаётся при старте. Разрешение на уведомления (Android 13+) запрашивается при первом включении уведомлений, а не при запуске.
- Debug: APK для разработки. Release: подписанный APK или AAB. Ключ подписи и `key.properties` не попадают в репозиторий.

### 8.5 Критерии приёмки Android

- Иконка приложения корректно выглядит на лаунчере, включая тематическую иконку Android 13+.
- Заставка светлая или тёмная в зависимости от темы телефона.
- Уведомление о публикации показывает белую иконку `ic_stat_contentpilot`.
- Release-сборка ходит в бэкенд только по HTTPS.
